# The data layer

<!-- Moved from CLAUDE.md on 2026-11-12 so it loads only when needed. Keep it current with the code it describes. -->

Read before changing `peloton/api.py`, `dashboard.py` (or a `dashboard_*.py` module), `cache.py` (`load_snapshot` is `_usable`, then the `_REPAIRS` table of per-key validators that drop a damaged entry and keep the cache, then the name-facts pair check; add a new persisted key's validator there), `workouts/workout_log.py`, `workouts/activity.py`, `stats/journey.py`, `stats/username_facts.py` or a `feeds/` parser. `peloton/` keeps the infrastructure (config, cache, dashboard, demo, notify, schedule, screen times) and the shared helpers `selection` and `timestamps`; the rest is three subpackages, layered `workouts` > `stats` > `feeds` (a lower one never imports a higher one; import-linter's layers contract in `pyproject.toml`): `feeds/` parses what the API sends (challenges, club, booked classes, goals, instructors), `stats/` works out lifetime and name-page figures (journey, totals, summaries, records, username facts), `workouts/` is the workout log and everything compared over it (activity, rows, features, compare, insights). The name page's built facts and idea list are in `docs/NAME-PAGE-FACTS.md`.

- `peloton/api.py` — `PelotonClient`: raw HTTP calls to `api.onepeloton.com`, using a `requests.Session` from `make_session(token_path)` (Bearer token; the file is called `cookies*.txt` for history). Records `login_required` on HTTP 401.
- `peloton/dashboard*.py` — `Dashboard` (`dashboard.py`) is one class built from mixins, so every method shares one `self` and the same locks (`_lock` for the snapshot, `_refresh_lock` for one refresh at a time, `_cache_write_lock`, `_log_lock`, `_rows_lock`); a patch must target the module a name is looked up in. `dashboard.py`: init, snapshot accessors, the refresh loop (`_refresh_once` and its steps), login and stale flags. `dashboard_fetch.py` (`FetchMixin`): recent workouts, strength detail, the challenges / bookings / club fetches and their retry constants. `dashboard_insight.py` (`InsightMixin`): a workout's insight views (milestone plus row-store comparison). `dashboard_history.py` (`HistoryMixin`): log-derived figures, the count check, the history walk (`HISTORY_BATCH_PAUSE_SECONDS`). `dashboard_celebrations.py` (`CelebrationMixin`): PR and milestone due/acknowledge, name-page cool-down. `dashboard_state.py`: pure helpers for the snapshot's starting points (`initial_data`, `demo_values`, `prepare_cached`, `PROFILE_KEYS`, `slim_profile`, `with_demo_insight`). The cache file's bytes are pinned by `tests/test_dashboard_cache_format.py` (fixture `tests/fixtures/dashboard_cache_expected.json`; change it only with a `CACHE_VERSION` decision). `Dashboard`: background refresh thread, cache, failure counting and the stale/login flags the display reads. Each refresh: overview + the newest `recent_fetch_size` workouts (profile once a day), merged into the workout log; a `peloton-history` thread does the first full download (resumable, `history_batch_size` per batch) and count-mismatch re-walks.
- Strength tracker: for each finished strength class on the latest active day, `Dashboard._strength_detail` fetches the workout detail (`get_workout_detail`, `GET /api/workout/<id>?joins=ride,ride.instructor`) once, kept per workout in `_details` while its signature holds (same bound as the performance cache); a failed, missing or unfinished detail retries after `INSIGHT_RETRY_SECONDS`, only a 401 escapes. `summarize_workout(workout, perf, detail)` turns `movement_tracker_data.completed_movements_summary_data` into `summary['strength']` (`summaries.strength_tracker`: `completion_percentage` is the share of movements on target and `longest_streak` the most in a row, both checked on all 450 tracked classes in the raw dumps). The workout insights reuse that detail (`_workout_insight(..., detail)`), so with insights on there is no extra call; off, it's one call per strength class. Not in the workout log, so only the latest workouts have it and there's no `LOG_VERSION` bump. Coverage in the raw dumps, 2025 on: Joel 137 of 148 strength classes tracked, Jen 194 of 307.
- Challenges: `PelotonClient.get_current_challenges` (`GET /api/user/{id}/challenges/current?has_joined=true`; shapes and quirks in `docs/PELOTON-API.md`) is called from the refresh by `Dashboard._refresh_challenges`, only while `challenges` is in the rotation, at most every `CHALLENGES_REFRESH_SECONDS` (an hour: 24 calls a day per rider), and `CHALLENGES_RETRY_SECONDS` (15 min) after a failure, which keeps the last list and never fails the refresh (only a 401 escapes). A new token asks again at once. `peloton/feeds/challenges.py` (import-free) slims each entry to what the page draws (`slim_challenge`: short title, which keeps a monthly challenge's month as `NOV` and drops the year, value, Peloton's pre-formatted number when it is one, unit with `workouts` as `CLASSES`, current and next tier with trimmed titles, `Unearned` when there's none yet), published and cached as `challenges` (in `PERSISTED_KEYS`; `cache.py` drops a list with any entry `valid_challenge` rejects). Demo data has two (`_demo_challenge`).
- Club Peloton: `Dashboard._refresh_club`, only while `club` is in the rotation, calls `PelotonClient.get_club_score` (`GET https://members-score.onepeloton.com/v2/user/{id}/score`, ~8 KB, undocumented; shapes in `docs/PELOTON-API.md`) after the recent-workouts fetch when the newest workout's ID differs from the last check's, else every `CLUB_REFRESH_SECONDS` (6 h): about 4-10 calls a day per rider. Any failure, a 401 included, keeps the last figures, never fails the refresh and asks again after `CLUB_RETRY_SECONDS` (15 min); `get_club_score` goes round `_get`, so a 401 from that host never sets `login_required` while the main API takes the token. A 404 (no score) publishes `club.NOT_A_MEMBER`, which hides the page. A new token asks again at once. `peloton/feeds/club.py` (stdlib only) keeps `level`, `points`, `tier_min`/`tier_max` (the metal's range; `tier_max` None for Legend or when it's below the points), `marks` (where the tier's levels start, unless `ignore_segments_on_profile`), `next` and `to_next` (from the `segment_tiers_max_points` row whose `label` is the level, else the one the points fall in) and `boost_until` (an `active` boost's `expires_at` still ahead), published and cached as `club` (in `PERSISTED_KEYS`; `cache.py` drops a record `valid_club` rejects). `PROFILE_KEYS` keeps `/api/me`'s `badge_level` (0-10) for the page until the first score. Demo data: `demo.demo_club` (Gold III, a week of boost).
- Booked classes: `Dashboard._refresh_bookings`, only while `next_class` is in the rotation, calls `PelotonClient.get_reservations` (`GET /api/user/{id}/reservations`, a few hundred bytes) on every refresh (288 calls a day per rider at 300 s), then `get_scheduled_class` (`GET /api/peloton/{id}?joins=ride,ride.instructor`, ~7.7 KB; shapes in `docs/PELOTON-API.md`) once for each newly booked ID, kept in `_bookings` by ID while it stays booked (seeded from the cache, so a restart doesn't ask again); a cancelled ID drops out. A class whose details fail (or 404, or can't be shown) is skipped and asked again after `BOOKING_RETRY_SECONDS` (an hour); a failed reservations call keeps the last list; neither fails the refresh, only a 401 escapes. `peloton/feeds/booked_classes.py` (stdlib only) slims a class to `id`, `start`, `tag` (`ENCORE` if `is_encore`, else `LIVE` if `is_live`, else none), `discipline` (Peloton's `circuit`/`caesar` aliased), `minutes` and `instructor`, published sorted by start and cached as `booked_classes` (in `PERSISTED_KEYS`; `cache.py` drops a list `valid_bookings` rejects). A rescheduled class keeps its first-fetched start until it's rebooked (not seen to happen). Demo data has two (`demo.demo_bookings`, relative to now).
- `peloton/workouts/workout_log.py` — `WorkoutLog`: every workout as a slim row keyed by workout ID (`<cache>.workouts.json`). Instructor counts, journey miles and weekly progress are derived from it on each refresh by feeding `as_workout()` rows to the existing `merge_instructor_counts` / `merge_distance_totals` / `weekly_progress`, so a counting fix never needs a re-download. Instructor and distance figures stay empty until the backfill is complete. A row's `discipline` is the workout's own category (`selection.discipline_of`: the workout's `fitness_discipline`, then the class's), which is what Peloton's overview counts: Walk + Run classes became Running in October 2025 but earlier workouts stay Walking (LOG_VERSION 2, found 2026-11-08: 38 workouts, plus a Strength-logged Core Stretch, made the log disagree with the overview). To add a field: extend `trim()` and bump `LOG_VERSION` (one re-download per board). Design and measurements: `docs/WORKOUT-LOG-PLAN.md`.
- `peloton/stats/journey.py` — journey miles: the tally per discipline, and `journey_progress` (the leg, plus `groups`: BIKE / ROW / WALK/RUN via `MILE_GROUPS`; anything not bike or rower is WALK/RUN so every mile shows). `display/ui/journey_screen.py` draws it (redesigned 2026-11-08; `docs/64x32-NOTES.md`): each step opens with ~1 s of animation (`INTRO_SECONDS`, 20 fps), so tests and previews render settled frames.
- `peloton/workouts/activity.py` — per-day figures from the log: `streak_week_workouts` (streak-eligible workouts since Monday, for the weekend `streak_risk` page that replaces `streak`) and `daily_minutes` (12 weeks, for the `heatmap` page). `frame_stats` (`period_stats` for each of `frame_bounds`' windows: this week, last week, last 30 days, last 90 days, this year, last year, all time: workouts, minutes, per-discipline and per-instructor counts, different classes by `ride_id` and instructors, active days; rolling windows in the display timezone, never the calendar month, at Joel's request 2026-11-08, so the 1st of a month isn't empty) feed the name page, and only class-led workouts count in `period_stats`, `frame_stats` and `event_stats` (`class_led`: a non-empty text `ride.instructor.id`, which is empty on exactly the non-class workouts; not `ride_id` or the title; see `docs/NAME-PAGE-FACTS.md`), except active days: a frame's top-level `active_days` (and unfiltered `period_stats`) counts every completed, timed workout, so outdoor runs and walks are active days (`_stamped(class_only=False)`); the `by_*` sub-stats stay class-led; `frame_stats` also adds each frame's bests (`_bests`: busiest day/week/month, longest workout, bike output, Strive) and, for the 30- and 90-day frames, `block_rank` (against non-overlapping blocks back from today), and, for the 30-day, 90-day and year frames, `before` (workouts and minutes of the same stretch before; `comparison_window`: the year against last year up to today's date), and splits each frame in the same pass into `by_discipline` (the `SUBJECT_DISCIPLINES` most-done, 5) and `by_instructor` (`SUBJECT_INSTRUCTORS`, 3), each the same stats as `period_stats(..., discipline=, instructor=)`. All arrive in the snapshot via `WorkoutLog.derived` (`time_frames` only once the backfill is complete). `event_stats` (dates the events measure from: today, anniversary from the profile's `created_at` (kept in `PROFILE_KEYS`, passed as `member_since`), earlier years on today's date, each discipline's first/last/before-last day, the most-seen instructors' last class; in the snapshot as `events`, just the anniversary while the log is incomplete).
- `peloton/stats/username_facts.py` — the name page's highlights, chosen by score (step 6, 2026-11-08; THIS WEEK dropped at Joel's request, the Goals screen covers it): the total, two headlines of different `KINDS` groups, then an instructor top three, six highlights (30 s) when there's enough to say. Every fact from `frame_facts` (per frame in `FRAME_ORDER`, incl. `events`), `frame_subjects` (a most-done discipline as `CYCLING` / `50 WORKOUTS` / `IN 2026`, carrying its own top three) is a candidate with a `kind` (`rank`, `instructor:jess`, ...; the part before `:` picks the `KINDS` group and base score) and a `key` (`30d:rank`); `fact_score` adds a bonus (first place, size of a comparison's change, `when` within 14 days of the events' `today`, only for `RECORD_FRAMES` all/year: a recent busiest day inside 30 or 90 days says nothing) and subtracts the cool-down; `scored_facts` is the sorted list, with facts that read the same in several frames (same `kind` and `lines`) collapsed to the one scoring best before any cool-down (else resting it would bring a copy in), `username_details` takes the best, then the best of another group (the pinned `anniversary_fact` is the first headline all day), and the top three of the first chosen discipline headline, else `_general_ranking` turns through `frame_rankings` (all time, then each discipline's all-time top three, then the other frames). A discipline's lifetime count is not a headline (the Lifetime pages show it; Joel, 2026-11-08), and unique classes are no fact (a given; `period_stats` still counts them); the instructors count reads `N UNIQUE` / `INSTRUCTORS`. Cool-down: the dashboard's own saved counter, not the loop's pass index (which restarts at 0 and, with several riders, is the cycle count): `Dashboard.acknowledge_name_facts` (called by `run_display_loop` after the page, with `state['fact_keys']` = `shown_keys`: each fact's key and its `kind:` key) runs `record_name_facts`, saving `name_facts_passes` and `name_facts_shown` (`{key: count at showing}`, validated in `cache.py`); a fact loses `COOLDOWN_PENALTY` (100) and its kind `KIND_COOLDOWN_PENALTY` (40), wearing off evenly over `COOLDOWN_PASSES` (20) pages; without a counter in the snapshot (a preview) `pass_index` turns the top threes. `frame_facts` also has one fact per most-seen instructor (name over minutes), `_measure_facts` adds averages, the discipline share, rank and the bests (thresholds are named constants; none under 5 workouts) adds a comparison (`LAST 30 DAYS` / `19 WORKOUTS` / `UP FROM 12`, `DOWN FROM` when lower, `THIS YEAR` for the year; it replaces that frame's `total` while it shows, so the count is said once, and only when both sides have 5+ workouts and it changed 20% and 3+; `username_details` also never takes two headlines with the same label), and all time adds the cache's `best_weekly` streak. `scripts/list_facts.py` prints every fact for a log, its score, and the first passes with the cool-down applied (weights are tuned from real logs with it). Labels must fit 15 characters of the `stats` font (60 px): hence `MOST IN 30 DAYS` (exactly 15), shown only when it differs from the all-time top discipline; least-done was dropped at Joel's request 2026-11-08, and a discipline's ranking carries `short_label` (rank + last word, `3RD BOOTCAMP`) that `UsernameScreen` uses when the label doesn't fit. A value line wider than the 60 px room scrolls (`UsernameScreen.scroll_offset`: hold `SCROLL_HOLD_START`, glide at `SCROLL_SPEED`, hold, and back only if the highlight is long enough for the whole trip; the margins are blanked after drawing so the text slides under them), so long instructor names aren't clipped; labels still use `short_label`. Before scrolling, 64 rows wrap a too-wide first value line that has a count under it onto two lines (`UsernameScreen.wrap_two_lines`; the label rises `WRAP_LABEL_RISE` rows, name on `WRAPPED_BASELINES`, count where it was; a line that can't split still scrolls), and 32 rows (no spare rows, so the count stays) let a line of 61-64 px run edge to edge with no margin (`JERMAINE JOHNSON`, 64 px, 16 characters; the 4x6 font is fixed-width, so case makes no difference), scrolling only the rarer longer ones; the recent-workout page already wraps names itself. Analysis with real logs: the instructor names that exceed 60 px are 10 of 52 across both riders. Built facts and the idea list: `docs/NAME-PAGE-FACTS.md`. Step 5's `events` (`event_facts`, worded as sentences: `A YEAR AGO` / `YOU HAD 812` / `NOW 1,067` (`activity.event_stats` puts the log's `workouts_then` and `workouts_now` on each `on_this_day` entry; an older cache without them has no such fact), `WELCOME BACK` / `STRETCHING` / `1ST IN 286 DAYS`, `NEW DISCIPLINE`, `LAST ROW` / `52 DAYS AGO` (`_since_fact`, nouns in `SINCE_NOUNS`; over 15 characters it is `LAST` / `TREAD BOOTCAMP` / `52 DAYS AGO`), `LAST CLASS WITH` / `MATT WILPERS` / `74 DAYS AGO`; kinds and keys unchanged; thresholds are constants beside `MIN_EVENT_WORKOUTS`) score highest in `KINDS`; `anniversary_fact` is pinned.
