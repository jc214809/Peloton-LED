# The settings page

Read before changing anything in `settings_page/`, `utils/wifi_setup.py` or `display/ui/overlays/settings_pin.py`.

`python -m settings_page.server` (`peloton-settings.service`, port 8080, root, its own service so a config that stops the display can be fixed; ported from LightningLane-Live-LED's). `form.py` is config ⇄ form (`apply_form` runs one function per card, the ordered tuple `FORM_SECTIONS`, then the least-seconds checks and `validate_config`; `tests/test_settings_form_pin.py` compares full and partial forms on example configs with `tests/fixtures/settings_form_pin.json`, compact, values stored once by hash, one case per line (`tests/pin_fixture.py`); regenerate only for a deliberate change: `PIN_REGEN=1`; only shown keys change; requires the hidden `settings_form` field since unticked switches post nothing; every check is `peloton.config.validate_config` on a copy, so `load_config` and the page agree), `page/` the HTML, a package with one module per card (map below; inline CSS/JS, works without JS; rotation rows drag by a grip with pointer events (mouse and touch; arrow keys on the grip), a switched-off screen drops to the bottom and a switched-on one joins the end of the numbered ones; `tests/test_settings_form.py` parses it like a browser, and saving an unchanged page must load the same), `pins.py` the PIN gate, `server.py` stdlib HTTP (`Handler.do_POST` runs the shared checks, then dispatches by path through `PIN_POSTS` and `SETTINGS_POSTS` to one `_post_*` method each; `systemd_text.py` parses `systemctl show` times). Riders are matched by index plus a hidden name check; names, token/cache paths, `*_env` and the journey are never on the page. Logins card (`logins.py`, no HTTP/HTML): health from renewal's own files via `scripts/refresh_cookies.py` helpers (`token_status`, `load_refresh_chain`/`describe_chain`, the `.renewal-failed` marker honoured only while newer than the token, `.browser-attempt`, `token-alert-state.json`, `/etc/peloton-led/token-mode`), unit state from `systemctl show`; *Renew now* is `systemctl start --no-block peloton-token-refresh.service`; the Logins card shows renewal as labelled rows (`page.logins_section.renewal_status`, times via `systemctl show --timestamp=unix` → `systemd_text.unix_time`; a running one is followed by `/renew/status`), and each rider is a `<details class="rider-card">` (`page.logins_section._login_status`: closed while healthy, open when not), whose Email & password row is a `<details class="cred">` holding that rider's own form (only their `cred_<key>_*` fields; a 400 reopens it via `editing_rider`; Cancel is JS-only); renewal times come from `logins.renews_at` (first hourly check within `RENEW_BEFORE_S` of expiry; `CHECK_EVERY_S`/`RENEW_BEFORE_S` mirror the timer's `OnUnitActiveSec=1h` and the service's `--renew-before-hours 12`, and a test fails if they drift); the renewal timer is OnBootSec/OnUnitActiveSec, so systemd leaves `NextElapseUSecRealtime` blank and `Settings.next_elapse` reads `NextElapseUSecMonotonic` (a timespan since boot) instead, which is why PelotonPi once said "Not scheduled" while the timer ran; *Compact workout pages* is shown only on 64x32, so the form posts `COMPACT_SHOWN` beside it and `apply_form` leaves the saved value alone without it (an unticked switch posts nothing); the Rotation list's column headings (`ROTATION_COLUMNS`, ⓘ tooltips) sit outside the `<ol>` so the drag code never sees them; the top bar's Power menu (`page.shell.power_menu`, shown with Sign out, so not on the hotspot page; a `<details>` of one-button `_post` forms with `data-confirm`, so it works without JS and asks first with it) posts `action` to `/power` (`Handler._power`, `Settings.power`, `POWER_ACTIONS`): `restart-display` / `stop-display` / `start-display` (`systemctl <verb> --no-block <display unit>`; Start replaces Stop when `display_running` is False) and `reboot` / `poweroff` (`systemctl --no-block reboot|poweroff`); same-origin check, a PIN session even on the hotspot (like `/credentials`), 409 while an update runs, 400 for an unknown action, no systemctl → `?power=unavailable`, a failure → `?power=failed-<action>` with stderr in the log; reboot/poweroff send their message page *before* running the command (so a failure there is only logged); Pushover keys and the test alert are their own card (`page.alerts_section.alerts_card`, its form posts `card=alerts` to `/credentials`, outcomes `?alerts=`); credentials are write-only: `update_auth_env` rewrites only the changed lines (setup_config.py's quoting, 600, no .bak), the page only ever gets set/not-set, the log only names what changed, and `/credentials` needs a PIN session even on the hotspot. Relative token paths start from `--token-base` (/etc/peloton-led, as the display sees its config), not the checkout. PIN-page states live at `/signin`. The PIN goes to `/run/peloton-led-settings/pin` (`RuntimeDirectory`, group peloton-led, 0640) and `display/ui/overlays/settings_pin.py` draws it in `ScreenManager.tick`; `show_and_wait` repaints when it appears/goes, like the padlock. Wi-Fi: `utils/wifi_setup.py` reads comitup's `/run/comitup-state` (written by LLL's `board-setup.sh`); while `HOTSPOT`, a browser in 10.41.0.0/16 needs no PIN and `run_multi_user_loop` holds the `wifi_setup` screen each cycle. A hotspot after a cold boot with the saved Wi-Fi in range was a comitup/`wlan0` boot race (PelotonPi, 2026-11-11), fixed by LLL's `board-setup.sh` drop-in (`comitup.service.d/wait-for-wifi.conf`, LLL #222); updates don't add it, so troubleshooting in `docs/install.md` gives the hand steps. Save: validate, `.bak`, atomic write keeping owner/mode, then `restart_app`: `not_running` (manual board off) / `restarted` / `failed` / `saved` (no systemd). The display's config is a read-only bind of the checkout file, so the settings service gets the real path and its folder via its own `project-config.conf` drop-in; the atomic replace is picked up when the display restarts. Installer: `resolve_settings_page` (flag, else on unless installed-and-disabled), `start_settings_page` after `start_or_restart_display`.

Tokens come from `scripts/refresh_cookies.py` (browser login once, then Auth0 refresh tokens; see Pi config above).

The Timing card also holds `display.next_class_takeover_minutes` (*Class takeover*, minutes, `0` is off, `max` 10 from `booked_classes.TAKEOVER_MAX_MINUTES`; blank saves nothing, so the default 5 applies, `0` is saved as 0; `form.apply_form` via `set_or_drop`, checked by `validate_config`). It is board-wide, like the rotation switches. Its Rotation row's hint (`SCREENS`) mentions it; behaviour is in `docs/dev/ROTATION.md` (Next-class takeover).

Config validation (`peloton.config.validate_config`, which `load_config` and `apply_form` both call; the page shows its messages as they are) is table-driven: each check is a `Rule(key, ok, message)` row (`peloton/config_rules.py` holds `Rule`, `run` and the small predicates), in `_DISPLAY_RULES` (display.*, in the order errors are reported: the first failing row wins), `_MATRIX_RULES`, and `_USER_*_RULES` (per rider); weekly goals, milestones and the journey are shared row lists used for the display and each rider via the `{prefix}` in their messages. To check a new key, add one row where its error should rank, plus its default in `DEFAULTS` / `MATRIX_DEFAULTS`. What doesn't fit a row is a small function listed among the rows (unique names/tokens/paths, the retired-key and unknown-discipline warnings, the legacy font rewrite, milestone sorting, journey trimming). `tests/test_config_validation_messages.py` pins every message word for word, their order when two things are wrong, and the checked result of the example configs (fixtures in `tests/fixtures/config_validation/`); change a message and that test must change with it, deliberately. A rider's `token_path: null` crashes with an `AttributeError` instead of a message (pinned, not fixed).

## The page package (`settings_page/page/`)

Split from one 1,748-line `page.py` (code health plan, 2d) with no change to the HTML. That was proved by a 129-case pin of the whole page (every example config, a full one, and the notice, login, alert, update, insight, power and sign-in states) that passed on the old `page.py` and, unchanged, on the package; it lived only for that PR (commit "Pin the settings page's HTML before splitting page.py"), since 1.8 MB of golden HTML would have to be regenerated on every card change. To prove a later pure refactor the same way, restore it from that commit for the PR. Every module is under 600 lines (`tests/test_file_length.py`) and does one job:

- `__init__.py`: only re-exports what `server.py` and the tests import (`settings_page`, `pin_page`, `message_page`, `check_result`, `renewal_status`, `shows_for`, `_zone`, and the `SAVED`/`SENT`/`*_OUTCOMES`/`TOUCH_ICON` constants). Patch or import a name from the module that defines it, not from here.
- `assemble.py`: `settings_page()` (and `SECTIONS`, the table of contents): the notices, the cards outside the form, then the form's cards in order. Its `PLR0913` is kept: 18 arguments are what `server.Handler._page` passes.
- `shell.py`: `document`, the top bar, `power_menu`, `notices`, `message_page`, `pin_page`, and the `SAVED`/`SENT`/`POWER_OUTCOMES`/`TOUCH_ICON` constants.
- `widgets.py`: the small builders every card shares (`_field`, `_input`, `_number`, `_options`, `_switch`, `_section`, `_notice`, `_pill`, `_post`, `_secret_input`, `_zone`, `_at`). `_post` keeps its `PLR0913`: a signature change.
- `rotation_section.py`: the Rotation card and `shows_for` (one small function per screen, dispatched from `SHOWS`/`SHOWS_AFTER_TIME`).
- `form_sections.py`: General, Timing, Goals (with the per-rider rows), Milestones and Schedules.
- `hardware_sections.py`: Panel and Advanced (`_matrix_field`).
- `insights_section.py`, `logins_section.py` (`renewal_status`, rider cards), `alerts_section.py`, `updates_section.py` (`updates_card`, `check_result`): one per card that has its own state.
- `icons.py`, `style.py`, `script.py`: the icon paths and the inline CSS and JS as string constants.
- `form_fetch.js`: the form helper, read by `script.py` as `FORM_FETCH` (see below).

Modules import only from each other, `settings_page.form`/`logins`/`history`/`updates`/`logo`, `peloton` and `self_update`; none imports `display` or `driver` (`logo.py` already takes the logo art from `display.ui.logo_art`, and that is the only link).

## Forms are sent with fetch (no iPhone "Send Anyway")

The page is served over plain http, and Safari on iPhone warns "This form is not secure / Send Anyway" for any `<form method="post">` submitted that way (fetch gets no prompt). Every button on these pages is such a form (Save, Sign out, Show/Send a PIN, Sign in, the Power menu's, Renew now, the Pushover and rider credential forms, Send a test alert, Check/Update now/Roll back), so `page/form_fetch.js` sends each one with `fetch()`: same URL, the form's fields plus the pressed button's name, `credentials: 'same-origin'`. There is no `form.submit()` and no script-made form anywhere; keep it that way, because the helper only sees the `submit` events the browser fires.

- One helper, two listeners: a capture listener on `document` remembers each submit button's `disabled`/`innerHTML`, and a listener on `window` (so it runs after the form's and the document's own handlers, whichever script registered first) sends the form unless something already called `preventDefault`. That is how `data-confirm` (Roll back, Power menu, Remove keys) still works: a cancelled confirm sends nothing. Being document-level, a form the page adds later (the Updates card's own check inserts Update now) is covered.
- A redirect (every save, sign-in, sign-out and card action) is followed with `location.assign`, or `reload` when it lands on the page already open; fetch drops the `#fragment`, so it is put back from the form's `section.card[id]` (`#updates`, `#logins`, `#alerts`), only for a redirect to `/`. Any other answer (a "Not saved" page, a 403/409 message, the Power reboot message) replaces the document with `document.open/write/close`, so the result is what a plain post shows; the address stays on the page that was open (a reload shows that page, not the POST's URL).
- A board that can't be reached (fetch throws) puts the buttons back, clears `form.dataset.submitting` (so the unsaved-changes guard works again) and alerts. A restart in the middle of Update now/Roll back can land here when fetch follows the redirect while the settings service restarts; the page's own `/update/status` polling covers the normal case.
- Without JavaScript the forms post themselves exactly as before; the markup is unchanged. The server's checks are unchanged too: `Handler._same_origin` turns away a post whose `Origin` isn't the page's own host (fetch sends the page's `Origin`), and `Referrer-Policy: same-origin` stays; `tests/test_settings_form_fetch.py` pins both.
- Each page's script is wrapped in a `{ }` block (`script.SCRIPT` for the main page, `script.FORM_SCRIPT` for the sign-in page, the only other page with a form): a page the board answers with is written over the open one by `document.write` and runs its script in the same scope, so top-level `const`s would otherwise be declared twice. New top-level names in the page script go inside that block. Timers outlive `document.write`, so the renewal and update polls each start with `if (!form.isConnected) return;`: the replaced page's form is detached, its polls stop, and the new page starts its own (without it, a renewal poll failed on the missing `#renewal` and retried every 5 s beside the new page's).
- Tests: `tests/test_settings_form_fetch.py` runs the real `form_fetch.js` under Node with a faked browser (skipped if `node` is missing; CI has it): fields and credentials sent, redirect, same-page reload, anchors, document replace, refused confirm, unreachable board; plus checks that both scripts are valid JavaScript and carried by the pages, and the cross-origin POST refusals.
