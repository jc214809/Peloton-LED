## Running the App

```bash
# Emulator mode (development, no Raspberry Pi required)
./peloton_led.py --emulated

# With Peloton API data
./peloton_led.py --emulated --cookies cookies.txt

# Override username and screen duration
./peloton_led.py --emulated --username "YourName" --display-duration 10

# Hardware (Raspberry Pi with physical LED matrix)
sudo ./peloton_led.py
```

On a Mac, `config.json` (the Pi's, `/var/lib/peloton-led` paths) can't be used: run with `--config config.local.json` (gitignored; repo-relative token/cache paths, no `matrix.gpio_mapping`), steps in the README's "Running on your Mac with real data".

Key CLI flags: `--config <path>` (default: `config.json`), `--led-rows`, `--led-cols`, `--cookies`, `--username`, `--display-duration`.

Every `--led-*` flag also has a key in the top-level `matrix` config section (flag name minus `led-`, dashes to underscores; `MATRIX_DEFAULTS` in `peloton/config.py`). `utils.utils.matrix_settings` resolves flag → config → default, so the `--led-*` argparse defaults must stay `None`.

## Previewing Screens

```bash
# Whole rotation to a PNG contact sheet, no API calls (cache file or --demo)
python scripts/render_rotation.py --height 32 --cache cookies-joel-dashboard-cache.json --config config.json --out /tmp/joel-32.png
python scripts/render_rotation.py --height 64 --demo --out /tmp/demo-64.png
```

Both 64x64 and 64x32 are supported. 32-row layouts live behind `matrix.height < 64` checks in each screen; the 64x64 layout is the reference and must not change when adjusting 32 rows (compare `render_rotation.py --height 64` output byte for byte before/after). `docs/64x32-NOTES.md` records every 32-row difference and why.

## Releases and the updater

Branches: PRs go into `develop-beta` (made from main 2026-11-05; the old `develop` is stale, ignore it); a release is a `develop-beta` → `main` PR. `.github/workflows/auto-tag.yml` (`scripts/auto_tag.py`) tags each merge into develop-beta `vX.Y.N-beta` and main's merge `vX.(Y+1).0` (the first: v0.1.0, `update.MIN_RELEASE`) with a GitHub release listing each PR's `## Release notes`; tags only, never commits. `release-notes.yml` fails a PR without that section (`.github/pull_request_template.md`; "None" allowed; a develop-beta → main PR needs none). The notes are read from merge commit bodies, so merge with the PR description as the message (`gh pr merge --merge --body ...`, or the repo's "PR title and description" merge-message setting). `version.py` is `git describe` (fallback `SCRIPT_VERSION`; `/opt/peloton-led` has no git). `tests.yml` runs on develop-beta pushes because the Beta channel waits for the tip's CI.

`self_update/` (ported from LightningLane-Live-LED's, 2026-11-05) runs from the **checkout**, not `/opt/peloton-led`, with `/opt/peloton-led/venv/bin/python`: the installer's `/usr/local/bin/peloton-update` (status/check/update/rollback/recover, `--channel beta`) and `peloton-rollback` `cd` there. `update.py` decides (channels `releases`/`beta`; pre-flight: free space, throttling, clean checkout, GitHub; rollback point in `/var/lib/peloton-update`: commit/branch, pip freeze, the live config (`live_config`: the checkout's `config.json`, else `/etc/peloton-led/config.json`), `display_running`), `board.py` runs git (as the checkout's owner), pip and `peloton-install.sh --skip-packages --skip-matrix [--skip-requirements]` (pip only if `requirements.txt` or `requirements-auth.txt` changed; no mode flags, so the board keeps its own), `github.py` the unauthenticated API, `state.py` phases (`UNFINISHED` blocks the next update; `peloton-update-recover.service` rolls one back at boot). Health within 5 min: a display that was running before the update must write `utils/heartbeat.py`'s `/run/peloton-led/health` (beaten at the end of each `show_and_wait`; the folder is `peloton-led.service`'s `RuntimeDirectory`, root:peloton-led 0770, so it survives the privilege drop; no folder → no write, as on a dev machine) with no systemd restart; a manual-mode display that was off stays off and isn't checked; an enabled settings page must answer on 8080. Failure → rollback (old commit, freeze, config) + Pushover via `auth.env`'s keys (`notify.send_pushover`). A version without `self_update/` is never installed. The settings page's Updates card (`settings_page/updates.py`): a check is a dry run in the settings process (git fetch as the checkout's owner, so the installer's drop-in gives it `PELOTON_CHECKOUT` and `ReadWritePaths=<checkout>/.git`; `/opt` gets `self_update/` and `version.py` copies for the import); Update now / Roll back go to `systemd-run --unit=peloton-update` (an update restarts the settings service); Save is refused (409) while one runs; the last outcome is `outcome.json`. No checkout (`default_checkout` finds no `.git`) → no card and no `/update/*` routes.

## Pi config

On the Pi, the checkout's `config.json` is the live config: the installer writes `project-config.conf` drop-ins (`BindReadOnlyPaths=-<checkout>/config.json:/etc/peloton-led/config.json`) for `peloton-led.service` and `peloton-token-refresh.service`, because `ProtectHome=true` hides `/home`. The file must use `/var/lib/peloton-led/...` token/cache paths. `config.json` is untracked; `config.json-example` is the template.

Token renewal (`scripts/refresh_cookies.py --ensure`) prefers the Auth0 refresh token saved beside each token file (`cookies-x.refresh.json`). Auth0 rotates it on every use and rejects reuse with `invalid_grant`, so persist the new one before anything else, never share one file between machines, and never retry Chromium hourly after `invalid_grant` (slow boards would fail every time): a board with Playwright/Chromium and credentials tries one browser login per day (`<stem>.browser-attempt` records the last try, written before starting); `--no-browser` boards never do. Each refresh file also records `chain_started_at` and `renewals`, carried through every rotation (a new login starts a new chain). `--status` and the `invalid_grant` error report the chain's age, which is how we learn Auth0's real chain lifetime. `--ensure` reports each run to `peloton/notify.py`, which sends Pushover alerts (`PUSHOVER_APP_TOKEN`/`PUSHOVER_USER_KEY` in auth.env) rate-limited by `token-alert-state.json` beside the tokens: second failure in a row or `invalid_grant`, then daily, plus one recovery notice. When renewal raises `LoginRequired` (incl. `RefreshTokenRejected`) it writes `<stem>.renewal-failed`; `Dashboard.login_indicator_required` shows the padlock from it (checked every 30 s, ignored once the token file is newer), but the refresh loop keeps using `login_required` so data keeps updating on the still-valid token. `scripts/seed_board.sh user@board` seeds, copies and installs a per-board pair from the Mac (via `--seed-dir`); `peloton-install.sh --no-browser` skips Chromium/Playwright. The installer defaults to manual mode (not started at boot or during install; `--start-at-boot` opts in), except that an upgrade with neither flag keeps a board already enabled at boot (`resolve_start_mode`). It also picks the token mode (`resolve_token_mode`): a flag wins (`--auto-token`/`--no-browser`/`--no-auto-token`), else a renewing mode the board already has — saved in `/etc/peloton-led/token-mode` as `<mode> <flag|auto>` (written by `save_token_mode` as soon as `/etc/peloton-led` exists, so a failed install keeps it), or, if `peloton-led.service` is installed without that file, inferred from the timer/`manual.conf` and whether the venv imports Playwright — else the hardware (32-bit `getconf LONG_BIT` or under 768 MB → `no-browser`, otherwise `browser`). Renewal stays off only with origin `flag` (`--no-auto-token`): before that flag existed, "off" just meant an upgrade ran without `--auto-token`, so a bare saved `none` (the first version's format) or an older board without renewal gets the hardware's mode. `peloton-led.service` passes no `--led-*` flags (a flag beats config, so the old `--led-gpio-mapping adafruit-hat` hid the config's value); `matrix.gpio_mapping` comes from config (`packaging/config.pi.json` sets `adafruit-hat`), and `check_gpio_mapping` stops the installer before any change if the live config lacks it. `peloton-led.service` starts as `User=root`/`Group=peloton-led` so the driver can map `/dev/mem` (the PWM pulse `adafruit-hat-pwm` needs, and the 1 MHz timer); as an unprivileged user the driver falls back to `/dev/gpiomem` and `-pwm` exits with "Need root". `PELOTON_MATRIX_USER=peloton-led` makes `led_matrix_options` set `drop_priv_user/group`, so the driver drops right after creating the matrix (before `configured_profiles` touches tokens/cache), and `ensure_privileges_dropped` exits if it's still root (the driver ignores a failed drop). Anything moved ahead of the `RGBMatrix(...)` call in `main()` runs as root. `adafruit-hat-pwm` also needs the onboard audio off (`dtparam=audio=off` + `blacklist snd_bcm2835`): the driver exits with a `snd_bcm2835` message otherwise. `check_pwm_audio` (after `check_gpio_mapping`, which records `GPIO_MAPPING`) asks before doing that and exits unchanged on no or without a tty; tests stub `is_interactive` and override `PROC_MODULES`/`BOOT_CONFIG`/`MODPROBE_DIR`. The boot partition is FAT, so no `cp -p` there. Blank-panel debugging on PelotonPi (2026-11-01) hit "Need root" first, then would have hit the audio; the jumper was fine. Troubleshooting entry in `docs/install.md`. `start_or_restart_display` restarts a display that was running when the install began even in manual/`--no-start` mode.

The installer builds `rpi-rgb-led-matrix` from upstream master, whose Python binding includes Pillow's private `Imaging.h`. `scripts/fetch_pillow_headers.py` pulls headers from the PyPI sdist of the exact Pillow in the venv (passed via `CFLAGS`); don't swap in Debian's `python3-pil` headers, since Pillow 12+ changed the struct layout the binding reads.

## Architecture

### Entry Point & Display Loop

`peloton_led.py` is the sole entry point. It:
1. Loads `config.json`, builds a `PelotonClient` from `cookies.txt`
2. Creates the `RGBMatrix` (hardware or emulator) and initializes fonts
3. Registers screens with `ScreenManager`, shows a startup logo, then enters the display loop
4. The loop cycles: logo → username → recent workout disciplines → all-time discipline totals

A reached milestone (`dashboard.pending_milestones`) is celebrated by `display/ui/celebration_screen.py` (`CelebrationScreen`: confetti and a rising trophy, then the number with a small raised ordinal ending (`_ordinal_line`; `_CAP_HEIGHTS` lines it up and `_COMMA_INK` closes up the comma in `2,000`, both measured once since the Pi's fonts can't be measured by drawing), or a headline / noun / subtitle, confetti drawn first so the trophy and text paint over it, every off pixel fair game; 20 fps via `frame_seconds`, which `show_and_wait` honours; `ordinal`; `milestone_noun` for the total, `discipline_noun` for a discipline's (a bootcamp keeps its own name, and `_noun_line` falls back to the last word, `BOOTCAMP`, where it doesn't fit)). `build_rotation_pages` puts it first, whatever the `milestones` section's place, and only one per pass: the newest pending total, or a discipline's (`pending_discipline_milestones`), taking turns by `pass_index` when several are due; `acknowledge_milestone` retires older pending ones and records the first showing in the cache's `milestone_shown_at`; it keeps showing until midnight that day (`goals.local_date` in `display.timezone`, else the profile's, else UTC), then moves to `celebrated_milestones`. Per-discipline milestones (`peloton/goals.py`: targets 25, 50, 100, then every 100, from Peloton's overview `totals`, not the workout log, so they match the Lifetime pages and need no backfill) are keyed `strength:500` and kept apart in `celebrated_discipline_milestones` / `discipline_milestone_shown_at`, so the old int-only `celebrated_milestones` check never sees a string; `acknowledge_milestone` takes either. The `next_milestone` section is one countdown for the total and every discipline (merged 2026-11-08 at Joel's request; there is no separate discipline section): `goals.upcoming_milestones` lists whatever is within `display.milestone_within` (5) of its target (the total's from `next_milestone`: configured `milestones`, else `milestone_step`), closest first (the total wins a tie), at most `milestone_pages` (3), so usually none. Each is a `countdown` page drawn by `display/ui/countdown_screen.py` (64 rows `3 TO GO / 600TH / RIDE`, the celebration's `discipline_noun`, the total `WORKOUT`; 32 rows keep `3 MORE / TO 600 / CYCLING`, the total `WORKOUTS`; the name in `lifetime_overview.discipline_color`; `bold`/`title_bold` fonts, 7x13B and 6x13B on 64 rows; the name is 6x9 on 32 rows, since 5x8's narrow G and T spaced out `S TRENG TH`; `celebration_screen.ordinal_line`). A discipline's celebration uses the same fixed `STEP_CELEBRATION_WINDOW` (10) as the total's step; the old `discipline_milestone_celebrate_within` setting was dropped 2026-11-08 (ignored if present; `settings_page.form.RETIRED_DISPLAY_KEYS` removes it on save). The settings page's Milestones card (`milestone-settings`, after Goals) holds `milestones`, `milestone_step`, `milestone_within`, `milestone_pages` and each rider's `milestones`; Goals keeps weekly goals, the streak reminder and each rider's name and goals. `render_rotation.PreviewDashboard` has no celebration history, so it only celebrates a total milestone crossed within that window (it used to show 2,000TH at 2,123). The demo data has Rowing at 22 and Running at 204 so `--demo` shows both a countdown and a celebration.

`run_multi_user_loop` plays the logo (`display.logo_duration` seconds, unless `display.show_logo` is false) before each rider's rotation except the first one after start-up, so a single-rider board shows it once per cycle.

Screen times live in `peloton/screen_times.py` (import-free, so the settings service uses it too): `page_seconds` is each screen's configured time (`screen_durations`, else its fallback; Total workouts uses Lifetime's) raised to what it needs (`least_seconds`: 5 s a highlight on the name page (`HIGHLIGHT_SECONDS`, 2026-11-09), 12 s for Head to head on 32 rows, 8 s for the journey's two steps on 32 rows, 5 for Lifetime, 5.8 for a celebration, else 1). A time is never 0 (agreed with Joel 2026-11-08): hiding a screen is leaving it out of `rotation`, and the logo has `show_logo`. `retire_zero_times` turns an older config's 0s into those switches, in `validate_config` (with a warning), in `apply_form` (so a save writes it) and when the settings page renders. Name and highlights, Head to head (64x32) and the journey (64x32: the trip, then miles by type, only with 2+ groups) share their page's time across their frames (`detail_seconds` / `stat_seconds` / `step_seconds` in the state), holding the last frame rather than starting over. The settings page's Rotation rows show a "Shows:" line from `page.shows_for` (the same functions; `test_screen_times.py` checks it against `build_rotation_pages`), each box's `min` is `least_seconds` for the panel, a lower saved value shows and saves raised, and Latest workouts has no box (each workout page lasts every stat once). The two-page 64x32 "compact" workout layout was removed 2026-11-08 at Joel's request ("compact is stupid"): `compact_workout_pages`, `last_workout_duration` and `screen_durations.latest_workouts` still load and do nothing, and `form.RETIRED_DISPLAY_KEYS` drops them on save. Loop tests use the `instant_clock` fixture (tests/conftest.py) instead of 0-second pages.

The loop is intentionally network-free after startup — all data is prefetched before `run_display_loop()` is called.

On a multi-rider board, `configured_profiles` gives each profile its own `display` (the shared section with the rider's `weekly_goals`, `milestones` and `journey` over it), and `run_multi_user_loop` must pass that, not the shared one, to each rider's `run_display_loop`: until 2026-11-04 it passed the shared one, so per-rider goal pages never showed. `render_rotation.py` hard-codes its own goals, so it can't catch this; `test_each_rider_rotation_uses_their_own_goals_milestones_and_journey` does.

### Driver Abstraction (`driver/`)

`driver/__init__.py` replaces the `driver` module in `sys.modules` with a `DriverWrapper` instance. When `--emulated` is passed (or tests are running), it imports `RGBMatrixEmulator`; otherwise it tries to import `rgbmatrix` (the native Raspberry Pi library) and falls back to the emulator. All code imports `from driver import RGBMatrix, graphics, ...` transparently.

### Screen System (`display/ui/`)

All screens implement the `Screen` ABC (`display/ui/screen.py`):
- `on_enter(matrix, state)` — called when screen becomes active
- `render(matrix, state)` — draws to the matrix
- `update(dt)` — optional animation tick
- `on_exit(matrix)` — clears the matrix by default

`ScreenManager` (`display/ui/manager.py`) holds a registry of named screens, manages transitions (calling `on_exit`/`on_enter`), and drives `tick()` calls. Screens are registered with `manager.register(name, ScreenInstance)` and shown with `manager.show(name, state)`.

`show_and_wait(manager, name, state, duration)` in `peloton_led.py` is the standard way to display a screen for a fixed duration.

Workout-page stats come from `_stat_details` in `display/ui/last_workout_screen.py` (routed by equipment: bike, tread/outdoor, row, everything else). Number formats match the Peloton app (`_fmt_strive`, `_fmt_distance`, `_fmt_output`, `_whole` rounds half up). `docs/DATA-POINTS.md` records which stats Peloton sends per equipment (from the raw responses in `perf_graphs/`) against which the board shows, plus stats/screens per workout; update it when changing `_stat_details`. After the stats, `rotating_details` appends chart slides (`kind`): `graph`, `zones`, `muscles` (top 3 from `summaries.muscle_groups`; only for disciplines in `MUSCLE_DISCIPLINES`, just Strength for now, though most workouts carry `muscle_group_score`); each holds `GRAPH_FRAME_EXTRA_SECONDS` longer, and `build_rotation_pages` sizes the page from the same list.

A PR celebration (`pr` page after a record workout) is windowed like a milestone but rolling, not to midnight (Joel, 2026-11-09): `Dashboard.should_celebrate_pr` is true for `PR_CELEBRATION_SECONDS` (24 h) after the first showing (`pr_shown_at`, `acknowledge_pr` via `_acknowledge`; then `celebrated_pr_ids`). `display.pr_max_age_days` (default null, config-only, not on the settings page) skips a PR whose summary `workout_at` is older; a cached summary without `workout_at` is never skipped.

### Peloton API Layer

- `peloton/api.py` — `PelotonClient`: raw HTTP calls to `api.onepeloton.com`, using a `requests.Session` from `make_session(token_path)` (Bearer token; the file is called `cookies*.txt` for history). Records `login_required` on HTTP 401.
- `peloton/dashboard.py` — `Dashboard`: background refresh thread, cache, failure counting and the stale/login flags the display reads. Each refresh: overview + the newest `recent_fetch_size` workouts (profile once a day), merged into the workout log; a `peloton-history` thread does the first full download (resumable, `history_batch_size` per batch) and count-mismatch re-walks.
- `peloton/workout_log.py` — `WorkoutLog`: every workout as a slim row keyed by workout ID (`<cache>.workouts.json`). Instructor counts, journey miles and weekly progress are derived from it on each refresh by feeding `as_workout()` rows to the existing `merge_instructor_counts` / `merge_distance_totals` / `weekly_progress`, so a counting fix never needs a re-download. Instructor and distance figures stay empty until the backfill is complete. A row's `discipline` is the workout's own category (`selection.discipline_of`: the workout's `fitness_discipline`, then the class's), which is what Peloton's overview counts: Walk + Run classes became Running in October 2025 but earlier workouts stay Walking (LOG_VERSION 2, found 2026-11-08: 38 workouts, plus a Strength-logged Core Stretch, made the log disagree with the overview). To add a field: extend `trim()` and bump `LOG_VERSION` (one re-download per board). Design and measurements: `docs/WORKOUT-LOG-PLAN.md`.
- `peloton/journey.py` — journey miles: the tally per discipline, and `journey_progress` (the leg, plus `groups`: BIKE / ROW / WALK/RUN via `MILE_GROUPS`; anything not bike or rower is WALK/RUN so every mile shows). `display/ui/journey_screen.py` draws it (redesigned 2026-11-08; `docs/64x32-NOTES.md`): each step opens with ~1 s of animation (`INTRO_SECONDS`, 20 fps), so tests and previews render settled frames.
- `peloton/activity.py` — per-day figures from the log: `streak_week_workouts` (streak-eligible workouts since Monday, for the weekend `streak_risk` page that replaces `streak`) and `daily_minutes` (12 weeks, for the `heatmap` page). `frame_stats` (`period_stats` for each of `frame_bounds`' windows: this week, last week, last 30 days, last 90 days, this year, last year, all time: workouts, minutes, per-discipline and per-instructor counts, different classes by `ride_id` and instructors, active days; rolling windows in the display timezone, never the calendar month, at Joel's request 2026-11-08, so the 1st of a month isn't empty) feed the name page; `frame_stats` also adds each frame's bests (`_bests`: busiest day/week/month, longest workout, bike output, Strive) and, for the 30- and 90-day frames, `block_rank` (against non-overlapping blocks back from today), and, for the 30-day, 90-day and year frames, `before` (workouts and minutes of the same stretch before; `comparison_window`: the year against last year up to today's date), and splits each frame in the same pass into `by_discipline` (the `SUBJECT_DISCIPLINES` most-done, 5) and `by_instructor` (`SUBJECT_INSTRUCTORS`, 3), each the same stats as `period_stats(..., discipline=, instructor=)`. All arrive in the snapshot via `WorkoutLog.derived` (`time_frames` only once the backfill is complete). `event_stats` (dates the events measure from: today, anniversary from the profile's `created_at` (kept in `PROFILE_KEYS`, passed as `member_since`), earlier years on today's date, each discipline's first/last/before-last day, the most-seen instructors' last class; in the snapshot as `events`, just the anniversary while the log is incomplete).
- `peloton/username_facts.py` — the name page's highlights, chosen by score (step 6, 2026-11-08; THIS WEEK dropped at Joel's request, the Goals screen covers it): the total, two headlines of different `KINDS` groups, then an instructor top three, six highlights (30 s) when there's enough to say. Every fact from `frame_facts` (per frame in `FRAME_ORDER`, incl. `events`), `frame_subjects` (a most-done discipline as `CYCLING` / `50 WORKOUTS` / `IN 2026`, carrying its own top three) is a candidate with a `kind` (`rank`, `instructor:jess`, ...; the part before `:` picks the `KINDS` group and base score) and a `key` (`30d:rank`); `fact_score` adds a bonus (first place, size of a comparison's change, `when` within 14 days of the events' `today`, only for `RECORD_FRAMES` all/year: a recent busiest day inside 30 or 90 days says nothing) and subtracts the cool-down; `scored_facts` is the sorted list, with facts that read the same in several frames (same `kind` and `lines`) collapsed to the one scoring best before any cool-down (else resting it would bring a copy in), `username_details` takes the best, then the best of another group (the pinned `anniversary_fact` is the first headline all day), and the top three of the first chosen discipline headline, else `_general_ranking` turns through `frame_rankings` (all time, then each discipline's all-time top three, then the other frames). A discipline's lifetime count is not a headline (the Lifetime pages show it; Joel, 2026-11-08), and unique classes are no fact (a given; `period_stats` still counts them); the instructors count reads `N UNIQUE` / `INSTRUCTORS`. Cool-down: the dashboard's own saved counter, not the loop's pass index (which restarts at 0 and, with several riders, is the cycle count): `Dashboard.acknowledge_name_facts` (called by `run_display_loop` after the page, with `state['fact_keys']` = `shown_keys`: each fact's key and its `kind:` key) runs `record_name_facts`, saving `name_facts_passes` and `name_facts_shown` (`{key: count at showing}`, validated in `cache.py`); a fact loses `COOLDOWN_PENALTY` (100) and its kind `KIND_COOLDOWN_PENALTY` (40), wearing off evenly over `COOLDOWN_PASSES` (20) pages; without a counter in the snapshot (a preview) `pass_index` turns the top threes. `frame_facts` also has one fact per most-seen instructor (name over minutes), `_measure_facts` adds averages, the discipline share, rank and the bests (thresholds are named constants; none under 5 workouts) adds a comparison (`VS 30 BEFORE` / `412 VS 380` / `+32 WORKOUTS`, only when both sides have 5+ workouts and it changed 20% and 3+), and all time adds the cache's `best_weekly` streak. `scripts/list_facts.py` prints every fact for a log, its score, and the first passes with the cool-down applied (weights are tuned from real logs with it). Labels must fit 15 characters of the `stats` font (60 px): hence `MOST IN 30 DAYS` (exactly 15), shown only when it differs from the all-time top discipline; least-done was dropped at Joel's request 2026-11-08, and a discipline's ranking carries `short_label` (rank + last word, `3RD BOOTCAMP`) that `UsernameScreen` uses when the label doesn't fit. A value line wider than the 60 px room scrolls (`UsernameScreen.scroll_offset`: hold `SCROLL_HOLD_START`, glide at `SCROLL_SPEED`, hold, and back only if the highlight is long enough for the whole trip; the margins are blanked after drawing so the text slides under them), so long instructor names aren't clipped; labels still use `short_label`. Before scrolling, 64 rows wrap a too-wide first value line that has a count under it onto two lines (`UsernameScreen.wrap_two_lines`; the label rises `WRAP_LABEL_RISE` rows, name on `WRAPPED_BASELINES`, count where it was; a line that can't split still scrolls), and 32 rows (no spare rows, so the count stays) let a line of 61-64 px run edge to edge with no margin (`JERMAINE JOHNSON`, 64 px, 16 characters; the 4x6 font is fixed-width, so case makes no difference), scrolling only the rarer longer ones; the recent-workout page already wraps names itself. Analysis with real logs: the instructor names that exceed 60 px are 10 of 52 across both riders. Built facts and the idea list: `docs/NAME-PAGE-FACTS.md`. Step 5's `events` (`event_facts`: `ON THIS DAY`, `COMEBACK`, `NEW DISCIPLINE`, `SINCE`, `LAST CLASS WITH`; thresholds are constants beside `MIN_EVENT_WORKOUTS`) score highest in `KINDS`; `anniversary_fact` is pinned.

### Workout compare

After a workout, one to three plain insights against the rider's similar earlier workouts. Rules only, no model; the contract is `docs/fitness-analysis/WORKOUT-COMPARE-SPEC.md` (untracked, with `BUILD-PLAN.md` and the prototype `wc_*.py` scripts it was ported from). Four standard-library modules: `peloton/workout_features.py` (`build_row`: three raw responses (detail, performance graph, class details) → one row, `ROW_VERSION`; bike `plan` from the callout lines through the frozen `BIKE_CURVE`; strength `asks`), `workout_compare.py` (`is_peer`: same discipline, class type, mode (plain/arms/floor), outdoor, length within 30%, complete, earlier; bike arms rides within 1 arms section (4b); `baseline` 365 days, else 730; bike `fill_in` from plan-nearest classes when there are 2-4 real peers, flagged), `workout_insights.py` (`insights(target, rows)`: output/pace, callouts, strength weights (movement's own history first, then the weight category), heart-rate effort, then `too_few`/`nothing`; at most three) and `workout_rows.py` (`RowStore`: `<cache stem>.workout-rows.json` beside the workout log, atomic 0600; `RawFiles`: saved responses in the `training-data/<rider>/<id>.workout.json` / `<id>.json` / `rides/<ride_id>.json` layout, so a `ROW_VERSION` bump is `import_raw`, never a refetch; `sync`: newest first, 20 a run, `LoginRequired` on a 401). `scripts/workout_insights.py --rider joel --config config.local.json [--dry-run]` is the daily run (`--dry-run`: no API calls, no writes). The 15 real-workout expectations (`tests/test_workout_compare_real.py`) read the gitignored `tests/fixtures/workout_compare/real-rows.json` from `scripts/export_compare_fixtures.py` and skip without it (CI), since the repo is public; re-export after a `ROW_VERSION` bump. `training-data/` and `*.workout-rows.json` are gitignored.

The board shows at most 2 insights (`insight_lines.MAX_BOARD_INSIGHTS`, the first allowed codes in `insights()` order) after the latest-workout page's chart slides (`rotating_details`): on 64x64 a card (`insight_card`: the sentence, what it was compared with) then bars (`insight_bars`: headline, today against the usual / a share bar / blocks, the reason); on 64x32 the bars then the sentence in 1-2 pages of 3 lines (`insight_words`); every frame holds like a chart slide and drops the discipline title and heart-rate row (`LastWorkoutScreen._insight_frame` draws before either). `insight_lines.board_view(code, facts)` (import-free, wraps by characters: the `stats` font is a fixed 4 px, 15 characters a line) gives each insight's view; the dashboard stores the list as `summary['insights']` (`board_insights`), and `last_workout_screen.insight_views` validates it, since the cache can hold anything. A movement name on the reason line scrolls via `UsernameScreen.scroll_offset`. Insight text is a softened white (`_INSIGHT_TEXT` / `insight_lines.SOFT_WHITE`, 200, 205, 215), since 255 glares beside the coloured figures. Weights read `40LB`; the word after a colon is drawn `COLON_GAP_TRIM` px closer (`_draw_words`). The Mac text is unchanged; the facts it carries for the board are `n`/`real`/`reason`/`close` (output) and `noun`/`rate`/`usual_rate` (effort, Strive per minute). The frames are shown behind `display.workout_insights` (default false; the settings page's Workout insights card, `page.insights_card`, after Rotation; the demo/`render_rotation.py --demo` show canned insights with `--insights` or that key in `--config`). The card also lists each rider's history on the board (`settings_page/history.py`: `rows_paths` names each rider's store as the display does, via `config.user_cache_path`, which `configured_profiles` uses too; `rider_histories` counts `workout_rows.current_board_rows`, the rows the board compares with, cached by the file's mtime and size so a Pi Zero doesn't re-read megabytes each page load; states missing / old (an older `ROW_VERSION`) / unreadable / ready) and warns when the switch is on and a rider has none. `Settings.workout_history` returns None for a config it can't follow, and the card then shows only the switch. `Dashboard._workout_insight` builds a row for each new in-scope workout from the first refresh that sees it COMPLETE (workout detail + class details, once; the performance graph is the refresh's own; a failed or unfinished detail is not asked for again for `INSIGHT_RETRY_SECONDS`, an hour) and upserts it into the rider's `RowStore` (`/var/lib/peloton-led/<cache stem>.workout-rows.json`, loaded on first use and trimmed to `BOARD_DAYS`, 760, so it stays its seeded size). While the workout is settling (its first hour from `start_time`, when the graph is refetched each refresh) the details are kept in `_insight_settling` and each refresh rebuilds the row with the new graph, logging `changed while settling` when it differs (to learn whether Peloton revises a COMPLETE workout; Joel, 2026-11-11), and writing the store only then (a same-looking rebuild writes nothing, so a Pi Zero doesn't rewrite 1-2 MB every refresh of the hour); the first refresh after the hour rebuilds once more, then it stops. Views are cached per workout against `_rows_generation` and recomputed only when the store changed (peers are earlier workouts, so nothing else moves them), logging `insights changed`; only a 401 escapes, any other failure is logged and leaves no insight. Switch off: no store load, no extra calls, and cached `insights` keys are stripped at start-up; version 2's single `insight` key is dropped whatever the switch. No class details are stored (several MB measured per rider), so a class taken before still costs one call when its workout is new. The store is seeded from the Mac by `scripts/push_workout_rows.sh user@board` (builds via `scripts/build_board_rows.py`; the board's file names come from the board's config, `--board-config`, default `config.json`, since the Mac's cache names differ). Rows of an old `ROW_VERSION` are ignored on the board (no raw files there): re-push after a bump. Plan and decisions: `docs/fitness-analysis/BOARD-PLAN.md` (version 2) and `BOARD-SLIDE-PLAN.md` (the card + bars frames). Layout: `docs/64x32-NOTES.md`.

### Settings page (`settings_page/`)

`python -m settings_page.server` (`peloton-settings.service`, port 8080, root, its own service so a config that stops the display can be fixed; ported from LightningLane-Live-LED's). `form.py` is config ⇄ form (only shown keys change; requires the hidden `settings_form` field since unticked switches post nothing; every check is `peloton.config.validate_config` on a copy, so `load_config` and the page agree), `page.py` the HTML (inline CSS/JS, works without JS; rotation rows drag by a grip with pointer events (mouse and touch; arrow keys on the grip), a switched-off screen drops to the bottom and a switched-on one joins the end of the numbered ones; `tests/test_settings_form.py` parses it like a browser, and saving an unchanged page must load the same), `pins.py` the PIN gate, `server.py` stdlib HTTP. Riders are matched by index plus a hidden name check; names, token/cache paths, `*_env` and the journey are never on the page. Logins card (`logins.py`, no HTTP/HTML): health from renewal's own files via `scripts/refresh_cookies.py` helpers (`token_status`, `load_refresh_chain`/`describe_chain`, the `.renewal-failed` marker honoured only while newer than the token, `.browser-attempt`, `token-alert-state.json`, `/etc/peloton-led/token-mode`), unit state from `systemctl show`; *Renew now* is `systemctl start --no-block peloton-token-refresh.service`; the Logins card shows renewal as labelled rows (`page.renewal_status`, times via `systemctl show --timestamp=unix` → `server.unix_time`; a running one is followed by `/renew/status`), and each rider is a `<details class="rider-card">` (`page._login_status`: closed while healthy, open when not), whose Email & password row is a `<details class="cred">` holding that rider's own form (only their `cred_<key>_*` fields; a 400 reopens it via `editing_rider`; Cancel is JS-only); renewal times come from `logins.renews_at` (first hourly check within `RENEW_BEFORE_S` of expiry; `CHECK_EVERY_S`/`RENEW_BEFORE_S` mirror the timer's `OnUnitActiveSec=1h` and the service's `--renew-before-hours 12`, and a test fails if they drift); the renewal timer is OnBootSec/OnUnitActiveSec, so systemd leaves `NextElapseUSecRealtime` blank and `Settings.next_elapse` reads `NextElapseUSecMonotonic` (a timespan since boot) instead, which is why PelotonPi once said "Not scheduled" while the timer ran; *Compact workout pages* is shown only on 64x32, so the form posts `COMPACT_SHOWN` beside it and `apply_form` leaves the saved value alone without it (an unticked switch posts nothing); the Rotation list's column headings (`ROTATION_COLUMNS`, ⓘ tooltips) sit outside the `<ol>` so the drag code never sees them; Pushover keys and the test alert are their own card (`page.alerts_card`, its form posts `card=alerts` to `/credentials`, outcomes `?alerts=`); credentials are write-only: `update_auth_env` rewrites only the changed lines (setup_config.py's quoting, 600, no .bak), the page only ever gets set/not-set, the log only names what changed, and `/credentials` needs a PIN session even on the hotspot. Relative token paths start from `--token-base` (/etc/peloton-led, as the display sees its config), not the checkout. PIN-page states live at `/signin`. The PIN goes to `/run/peloton-led-settings/pin` (`RuntimeDirectory`, group peloton-led, 0640) and `display/ui/settings_pin.py` draws it in `ScreenManager.tick`; `show_and_wait` repaints when it appears/goes, like the padlock. Wi-Fi: `utils/wifi_setup.py` reads comitup's `/run/comitup-state` (written by LLL's `board-setup.sh`); while `HOTSPOT`, a browser in 10.41.0.0/16 needs no PIN and `run_multi_user_loop` holds the `wifi_setup` screen each cycle. Save: validate, `.bak`, atomic write keeping owner/mode, then `restart_app`: `not_running` (manual board off) / `restarted` / `failed` / `saved` (no systemd). The display's config is a read-only bind of the checkout file, so the settings service gets the real path and its folder via its own `project-config.conf` drop-in; the atomic replace is picked up when the display restarts. Installer: `resolve_settings_page` (flag, else on unless installed-and-disabled), `start_settings_page` after `start_or_restart_display`.

Tokens come from `scripts/refresh_cookies.py` (browser login once, then Auth0 refresh tokens; see Pi config above).

### Config (`config.json`)

Key display settings under `display`:
- `username` — fallback display name
- `font` — no longer used (`UsernameScreen` picks the largest font that fits); still validated (`discipline`, `info`, `titles`, `stats`, `countdown`; legacy `ride`/`park` map to `discipline`) so old configs load, and kept on save though the settings page doesn't show it
- `color` — `white`, `gold`, `red`, `disney_blue`, `down` (the settings page's General card offers the first four as *Text colour*, plus `down` when a config already has it)
- `duration` — username screen duration (seconds)
- `overview_duration` — per-discipline page duration (seconds)
- `per_workout_duration` — per-recent-workout page duration (seconds)
- `logo_path` — optional override for startup logo image
- `logo_duration` — startup logo display duration (seconds); `show_logo` false hides it

### Fonts & Colors (`display/display.py`)

`initialize_fonts(matrix_height)` loads `.bdf` fonts from `assets/fonts/patched/` into a global `loaded_fonts` dict, keyed by font name. Font selection is board-height-aware (32 vs 64 rows). Colors are defined as `graphics.Color` instances in `colors()`.

### Logo (`display/ui/logo_art.py`)

The startup logo (`LogoMaskScreen`) is drawn, not decoded: the red mark (`logo_art.MARK`, cropped from the 32-row art), PELOTON and L E D in the loaded fonts, and a zone bar in `ZONE_COLORS` (also the workout pages' `HR_ZONE_COLORS`). 64 rows stack them; fewer put the mark on the left. `display.logo_path` swaps in an image file (`LogoScreen`). `settings_page/logo.py` draws the settings page's icons from the same art (inline SVG for the header and favicon, `/apple-touch-icon.png` served without a PIN), so `logo_art` must stay import-free. `scripts/render_logo.py` regenerates `docs/logo.png` and the README's startup screenshot. `prepared_logos/` and the `prepare_image`/`postprocess_logos` scripts are only for `logo_path` images.

### Models (`models/`)

Typed workout data models for each discipline: `cycling.py`, `running.py`, `rowing.py`, `strength.py`, all extending `models/core.py`. Used by `peloton/summaries.py` to normalize raw API payloads into structured workout summaries.
